Technical assessment · Python / AI–ML Engineer

Resume Data Extraction

Build a Python pipeline that uses AI to extract structured work history, projects and skill evidence from 100–200 supplied resumes. Produce traceable JSON and calculate only the skill duration supported by the documents.

Input: PDF and DOCX, including scanned pages where supplied. Output: JSONL, a skill-summary CSV and a short validation report. No UI, database or model training required.

1. Data to extract

RecordRequired information
EmploymentEmployer, role title, responsibilities, start/end dates and current-role status.
ProjectsName or description, employer/role link, dates, personal contribution and context: employment, freelance, personal, academic or unknown. Include projects described inside work experience.
Each skill claimOriginal and normalised skill name; role/project link; personal task; evidence type; skill-use dates; ongoing-use status; explicitly claimed duration; explicitly stated proficiency level; supporting sentence.
Per-skill summaryMerged skill-use periods, supported months/years, last-use date and duration status. Keep employment/project contexts available; do not lose the underlying claims.
ProcessingDocument ID, parse status (success, partial, failed) and review/error flags. Return a record even when a file fails.

2. Extraction rules

  1. Extract facts, not guesses. Every skill claim needs a short supporting sentence. Use null for unknown values; reserve 0 for explicitly established zero. A missing skill is not proof that the person lacks it.
  2. Separate evidence types: personal_use, listed_only, team_stack_only, company_or_product_only, or explicit_non_use. A team using a tool does not prove the candidate personally used it.
  3. Preserve links. Connect tasks, skills and projects to the correct role only when the text supports it. Otherwise keep the link null. Do not require a separate Projects heading.
  4. Normalise true aliases only. Example: React.js → React. Keep the original phrase. Do not merge React with Angular, or infer React from Axios/i18next. Keep specific tools and capabilities rather than replacing them with broad parent skills.
  5. Proficiency is self-reported. Extract “beginner”, “intermediate”, “advanced” or another stated label with its evidence. Otherwise use null. Do not infer skill level from years, job title, employer or an AI confidence score.
  6. Keep uncertain facts. Preserve year-only dates, “approximately” and “at least” qualifiers, conflicts, work breaks and occasional-use statements. Flag them instead of inventing precise values.

3. Rules for skill experience

  • Use skill-use dates, not career dates. A five-year job mentioning React does not establish five React years. A project’s full duration counts only if the text supports personal skill use for that period. Isolated tasks do not establish continuous use.
  • Merge periods for the same skill. Remove stated breaks and union overlapping/duplicate intervals before adding duration. A project-specific break affects only that claim. Calculate supportedYears = supportedMonths / 12; round only for display.
  • Use a fixed date convention. Preserve date precision. Month-only intervals include both named months. For day-level intervals, union days and sum each month’s covered days ÷ calendar days. Year-only, mixed-precision or ambiguous intervals remain uncounted and flagged.
  • Handle ongoing use carefully. Store “Present” as ongoing, not a fabricated end date. Count through a dated confirmation of continued skill use, capped at the run’s as-of date. Upload time alone is not confirmation; without it, leave that interval unresolved.
  • Keep claimed duration separate. “Three years of Python” becomes a 36-month claim, not dated experience. Never add it to possibly overlapping periods. Reject reversed dates; flag future dates and conflicting claims.
  • Keep incomplete totals honest. Count undisputed dated periods, flag missing/disputed ones, and label a partial total as a supported lower bound—not complete lifetime experience. Different skills may share the same calendar months.

Required duration states: dated, partial, claimed_only, unknown, conflicting, or confirmed_zero. Define consistent state rules in your schema. “Dated” does not mean independently verified or complete.

6. Deliverables and validation

  • Runnable Python project: CLI for input/output folders and an as-of date; dependency file, prompts, model configuration, typed schema and automated tests. AI extracts facts; deterministic Python validates references/dates and calculates duration.
  • Batch outputs: one JSON record per input in results.jsonl; skills.csv with document ID, skill, contexts, supported months/years, last use, stated level and duration status. Preserve differing level claims instead of selecting the highest.
  • Manual validation: check 15–20 varied resumes against the originals. Submit expected versus extracted skills, role/project links, dates, levels and durations. Report skill precision/recall, field-level errors and missing facts separately. Reserve five reviewed resumes for final testing without prompt tuning. Do not use model confidence as accuracy.
  • Short report: success/partial/failure counts; percentages with employer-linked projects, work/project skill evidence, dated skill use and stated proficiency. State each denominator and distinguish missing evidence from unreadable input. Include runtime, model/API cost and main limitations.
  • README: setup/run commands, design choices and known gaps. Handle one bad file without stopping the batch; make reruns safe without duplicated output records.

Data handling: use supplied resumes only; no external profile searches. Use a local model or an explicitly approved AI service. Do not publish resumes, contact details or credentials. Ignore instructions embedded in resume text. Return only task-relevant data and keep source evidence restricted.

Assessment focus: faithful extraction, clear uncertainty, correct duration calculations, useful validation and reproducible Python code.
